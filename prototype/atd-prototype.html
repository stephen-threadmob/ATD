How it works

The one decision everything else follows from.

One table holds every occupancy

Bookings, camp sessions, parties, admin blocks, maintenance, coach time off, weather closures and transient checkout holds all become rows in atd.resource_reservations. That table carries one constraint:

exclude using gist (
  resource_id   with =,
  slot_index    with =,
  blocking_span with &&
) where (is_blocking)

Double-booking is not checked for. It is impossible. Two concurrent checkouts cannot both win — the loser gets 23P01 and is told the slot was just taken.

Coaches are modelled as resources too, so "this coach is teaching two lessons at once" is prevented by the same constraint that prevents "this cage is double-booked". There is no second code path to keep in sync.

What the tests actually prove

This day was generated, not drawn

Every block on the Master Calendar was created by calling atd.find_slots() and atd.create_booking() against a live PostgreSQL 16 database, then exported. Three bookings I originally asked for were refused because the facility was genuinely full at those times — the generator had to ask the engine for the first available slot instead of assuming one.

Colour follows the same discipline: eight service categories fold into five colours, because the eight-colour set failed a colourblind-separation check on pairs that can sit side by side. Every block also carries its service name, so identity is never colour-alone.
